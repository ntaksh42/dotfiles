# jp-deslop

日本語の文章で、読み手に推測と余計な読む手間を強いる書き方を、書くときに避け、書かれた後で直す。検出ルールは Zenn の技術記事（AI 普及前 250 本、2026 年 250 本）で出現率を測り、差が出たものだけを残している。

## 守るもの

書き直しの前後で、次の4つを同じに保つ。直したくなる箇所があっても、この4つが動くなら直さない。

- 論点: 何を言っている文か。「本質」を「目的」に取り替えない。
- 重み: どれを重く扱っているか。否定していたものを並列に格上げしない。
- 確度: どこまで言い切っているか。断定を推量に、推量を断定に変えない。
- 用途: 何のための文か。評価、説明、依頼、予定を取り替えない。

足さない。元の文と前後から分からない動作主、数値、原因、例、専門用語は補わない。足りない情報は本文に書かず、「保留」で書き手に尋ねる。

## 書くとき

自分が日本語の文章を書く場合は、書き終えてから直さず、最初から次を守る。このときは「変更点」「保留」を付けない。

- 動作主と対象を文に出す。「静かに壊れる」のような比喩動詞を使わず、起きる事象をそのまま書く。
- 結論から書く。前置き、予告、定型の結びを置かない。1文に1つの内容だけを入れる。
- 複数の動作や項目は、名詞を並べた体言止めにせず、動詞で書く。
- 太字と箇条書きは、並列の項目か、本当に目立たせたい語だけに使う。否定対比は、読者が実際に抱きそうな誤解にだけ使う。
- 事実にない数値、原因、例、補足説明を作らない。分からない点は、書き手に尋ねるか、分からないと書く。
- ファイルに保存する長文は、`jp_lint.py` で確かめ、warn が出たら直す。

短いチャット返信、コードコメント、1行のコミットメッセージには、ここまで重く適用しない。

## 依頼の範囲

- 「端的に」「短く」「冗長」: 「端的にする」を中心に直す。
- 「AI っぽさ」「脱臭」: 「直す対象」を中心に直す。
- 「読みやすく」「推敲」「仕上げ」: 両方を直す。
- 日本語の文章を書く依頼: 「書くとき」に従う。

## 直す対象

1. 比喩動詞と英語直訳。「黙って無視される」「静かに落ちていく」「安全側に倒す」「時間を溶かす」「地味に効く」「1つずつ潰す」など。字義どおりの事象に開く。比喩が帯びていた気持ち（後悔、目立たなさ、気づけなさ）は別の言葉で残す。例と言い換えは references/vocab.md。
2. 非生物主語の擬人化。道具や概念に意志や感情を持たせた文（「設計が語りかける」「ログが教えてくれる」）だけを直す。働きの説明（「このライブラリは入力を検証します」）は残す。
3. 過剰な名詞化。「〜の実施の検討。」のように名詞をつないだ文を、助詞を補って動詞の文に戻す。
4. 形式の水増し。裏付けのない太字、論理を分断する箇条書き、読者が抱いていない誤解を先に否定する「AではなくB」。否定が論点や重みを担うときは残し、言い回しだけ整える。
5. 予告だけの文と記号。「注目すべき点があります」は中身の文と1文にする。ダッシュ記号（— ― ─）は助詞や読点でつなぐ。

## 端的にする

目的は、同じ内容を読む手間を減らすこと。冗長な言い回しは AI 普及前の技術記事のほうが多く出るため、AI っぽさの指標ではなく別の軸として扱う。

削ってよいもの:
- 前置き、予告、定型の結び（「いかがでしたでしょうか」）。
- 直前の文を言い換えただけの文。
- 冗長な形。「することができる」→「できる」、「を行う」「を実施する」→動詞、「において」→「で」、「ということ」→「こと」。
- 二重表現（まず最初に、違和感を感じる）。
- 前の文から分かる主語や目的語の再掲。

削らないもの:
- 条件、数値、理由、手順、注意書き。
- 推量と限定（「かもしれない」「ほぼ」「原則」）。確度を担う。
- 長くても、元の文が重みを置いている部分。

短くしすぎない。名詞を並べた体言止め、助詞や接続を落とした電報文、決め台詞のような短文の挿入は、読み手の推測を増やす。複数の動作を列挙する文（再発防止策など）は、名詞に潰さず動詞のまま並べる。削減率は目標にしない。声に出して一度で読めて、1文が1つの内容を言っていれば足りる。迷ったら削らずに残す。

## 触らないもの

- 定着した慣用句（「肩を持つ」「気が重い」）と、字義どおりの用法（扉が壊れる、雪が溶ける、お腹を壊す）。目安は、2022 年以前の技術記事にも普通に出てくる言い方かどうか。
- 「本質」「解像度」「重要なのは」「参考になれば幸いです」。AI 普及前の記事のほうが多く、AI の指標ではない。論点を担うなら残す。
- 絵文字、日英間の半角空白、文末のコロン、箇条書きの多さ。AI 普及前と出現率に差がなく、書き手の癖と区別できない。元の文書がそうしているなら残し、AI が見出しや箇条書きの頭に足した装飾だけ外す。
- 技術用語としての「実測」「照合」「既定」。「効く」「回す」「拾う」も、キャッシュが効く、ジョブを回すのような技術的な用法は残す。

## 調子の統一

文書の調子は、混ざっているときだけ直す。そろっていれば触らない。

- 混ざりの例: 敬体と常体、主語のない「確認します」と「確認しておきましょう」、決まりの「〜とします」と評価の「〜ことが重要です」。
- 文書の多数派にそろえる。確度は上げない（勧めを義務にしない）。
- 同じ文末が3回続いても、AI らしさがなければ変えない。文をつなげて文末の数を減らさない。
- 決めきれないときは、もう一方の調子で書く場合の文末案を「保留」に1行で添える。

## 進め方

1. 把握する。段落ごとの話題、前の文との関係（理由、例示、補足）、元の調子、守る4つを確かめる。返答には出さない。
2. 書き直す。直す箇所が少ない文書は、ほとんど触らずに返す。
3. 機械で確かめる。長文やファイル保存のときに実行する。`<skill-dir>` は SKILL.md のあるディレクトリ。
   ```
   python <skill-dir>/scripts/jp_lint.py <ファイル> [--concise]
   ```
   出力は候補であり、合否ではない。論点を担う語や正当な専門用語は、指摘されても残す。修正は最大2回。`broken_bold` だけは表示が崩れるので必ず直す。`--concise` は冗長な言い回しの候補（hint）も出す。Python が使えないときは同じ観点を目視で確かめる。
4. 元の文と見比べる。足した情報、消えた前提、確度の変化、削りすぎで増えた推測がないかを確かめる。

## 返す形

````
## 推敲後

（本文）

## 変更点
- 旧 → 新（理由）。意味が動き得る変更、補ったもの、削った内容、調子をそろえたものだけを最大5点。なければ「なし」

## 保留
- 意味や重みを担うため残した表現とその理由、書き手に確かめたい点。合わせて最大3点。なければ見出しごと省く
````

絵文字は使わない。ファイルを直接編集する依頼のときは、本文を書き換えたうえで「変更点」と「保留」だけを返す。
