# plan-and-delegate

計画書には、実装役が自分では決められないことだけを書く。実装役は計画書の自分のタスクだけを読み、会話の経緯は知らない前提で書く。

## 1. 計画書を書く

置き場所はユーザーやリポジトリの決まりに従う。決まりが無ければスクラッチパッドに `plan-<題>.md` として置き、リポジトリにはコミットしない。

冒頭に次を書く。

- 目的: 何を作るかを 1 文で
- 方針: 設計の要点を 2〜3 文で
- 全体の制約: バージョン、命名、対応環境、守るべき既存の規約など、全タスクに効く条件を値のまま 1 行ずつ
- 見落としやすい入力: 仕様が触れていないが利用者が出会いそうな入力や状況を、起きやすい順に数件。それぞれを確かめるテストを担当タスクに入れる

タスクは次の形で書く。

```markdown
### タスク N: <部品の名前>
- ファイル: 作る `path/new.ts` / 変える `path/old.ts:120-145` / テスト `path/old.test.ts`
- 受け取るもの: 前のタスクが作る関数名・引数・戻り値の型
- 渡すもの: 後のタスクが使う関数名・引数・戻り値の型
- [ ] 失敗するテストを書く（テスト名と期待値をコードで）
- [ ] 実行して失敗を確かめる（コマンドと期待する出力）
- [ ] 実装する（シグネチャと置き場所。本体はアルゴリズムが決まらない場合だけ書く）
- [ ] 実行して通るのを確かめる（コマンドと期待する出力）
- [ ] コミットする
```

タスクの大きさは、査読役がそのタスクだけを差し戻せる単位にする。準備・設定・ドキュメントの作業は、それを必要とするタスクに含める。

## 2. 計画書を自分で見直す

- 依頼や仕様の各項目に、対応するタスクがあるか
- 「適切に処理する」「エッジケースに対応」「TBD」のように何も決めていない行がないか
- 前のタスクで決めた名前や型を、後のタスクが同じ綴りで使っているか
- 計画書が書くべきコードより長くなっていないか。長いなら本体をシグネチャとテストに置き換える

見直したら計画書の場所をユーザーに示し、承認を待つ。返事がないことは承認ではない。実装の進め方（サブエージェントで回すか、自分で実装するか）の推奨を 1 文で添える。

## 3. サブエージェントで回す

タスクごとに、新しい実装役を 1 つ起動する。実装役は並列に起動しない（同じファイルを取り合う）。

実装役への依頼に入れるもの:

- このタスクが全体のどこに当たるかを 1 行
- 計画書のパスとタスク番号。読む範囲は自分のタスクに限るよう指示する
- 前のタスクで実際に決まった名前や型のうち、計画書と違うもの
- 報告の形: 状態（完了 / 懸念あり / 情報不足 / 行き詰まり）、コミット、テスト結果の 1 行、懸念

前のタスクの経緯を依頼文に貼り続けない。実装役に要るのは自分のタスク、触れる境界、全体の制約だけである。

実装役が完了を報告したら、起動前に控えた `git rev-parse HEAD` からの差分をファイルに書き出し、査読役に渡す。査読役には計画書のタスク、実装役の報告、差分ファイル、全体の制約を渡し、次の順で判定させる。査読役に「この点は指摘しないで」と先回りして指示しない。

1. 計画書と仕様への適合を確認する。要件を満たしているか、足りない変更や余計な変更がないかを確かめる。
2. 1 段目が通ってから、コードの質を確認する。実装の正しさと単純さ、必要なテストがそろっているかを確かめる。

指摘があれば同じ実装役に直させ、修正差分を 1 段目から査読し直す。3 回直しても収まらない指摘は、計画書の進捗欄に記録して先へ進むか、ユーザーに判断を仰ぐ。

## モデルの選び方

起動のたびにモデルを明示する。省くとセッションのモデル（たいてい最も高価なもの）を引き継ぐ。

| 役割 | モデル |
|---|---|
| 計画書にコードがほぼ全部ある、1〜2 ファイルの機械的な実装 | haiku か sonnet |
| 複数ファイルにまたがる実装、査読 | sonnet |
| 設計判断が要る実装、最後の全体レビュー | opus |
| 3 回目以降の直し | 実装役より 1 段上 |

安いモデルは手数が増えて結局高くつくことがあるので、査読役は sonnet を下限にする。

## 進捗を計画書に残す

会話は要約で消えることがあるので、進捗は計画書のチェックボックスと末尾の進捗欄に書く。各タスクが済むたびに `タスク N: 完了 (<base7>..<head7>, 査読済み)` を追記する。実行中に計画書が決めていない小さな点を自分で決めたら、`判断: <決めたこと> — <理由>` を進捗欄に残す。結果を左右するあいまいさ、破壊的・不可逆な操作、push やマージなど外への影響がある操作は、決めずにユーザーに聞く。

## 最後に

全タスクが済んだら、ブランチ全体の差分を opus の査読役に一度見せる。そのうえで `verify-before-done` に従って検証を流し、結果を報告する。
