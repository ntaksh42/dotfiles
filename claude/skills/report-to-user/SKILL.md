# report-to-user — 報告・相談・HTMLレポート

結果を先に伝え、人が判断に必要な根拠を見渡せる形にする。Claude Code / Codex 共通。`<skill dir>` はこの SKILL.md のあるディレクトリで、スクリプトや参照資料はそこから相対で解決する。

## 返す形を選ぶ

返信を書き始める前に形を決める。会話に長文を書いてからシートへ移すと、同じ内容を 2 回書くことになる。下書きは書かず、書く予定の中身の見積もりを `scripts/choose-form.py` に渡し、1 行目の「形:」に従う:

```bash
python "<skill dir>/scripts/choose-form.py" --question "<ユーザーの問い>" --items 4 --chars 250 --lines 4 --decisions 1
```

`--items` は答えに並ぶ項目の数で、答えが 1 つなら 1 を渡す (渡さないと、一覧を求める問いは項目数が分からないものとしてシートになる)。`--kind` には list / compare / steps / commands / ui / manuscript / report を必要なときだけ渡す。会話の目安は 3 行・200 字・3 項目・要判断 1 問で、hook の上限 (5 行・300 字・5 項目) より狭い。迷う値は大きめに見積もる。

| 状況 | 形 |
|---|---|
| 短い結果・質問への回答 | 会話で結論、必要な根拠、注意点を返す |
| 記事・README など原稿そのものの依頼 | 原稿ファイルを渡す。報告シートへ変換しない |
| 会話の目安を超える報告・相談 | **報告シート** (下の「報告シート」) |
| HTML 保存・レポート保存の明示依頼 | **報告シート** に `--save` を付ける |
| UI の配置・レイアウト・画面遷移を見て選ぶ相談 | **比較シート** (`references/comparison-sheet.md`) |

ユーザーが形式を指定した場合はそれを優先する。

短いシートにするか詳細にするか、種別、保存先は選ばない。`new-sheet.py` が本文から決める: 本文の文章が 800 字以内ならシート、超えたら詳細 (要判断・優先の帯と長い表の畳みが付き、字数の上限は外れる)。詳細と `--save` は `output-config.toml` の保存先へ連番で残し、種別はタイトルと見出しの語から決める。

シートを出したら、会話には **結論 1 文とシートの場所だけ** を書く。判断・推奨・注意点・一覧はシートに書き、会話で要約し直さない。答えは会話で受ける。

## 報告の核

- 最初の 1 文に結果を書く。経緯から始めない。
- 根拠は file:line や参照 URL など読み手が開けるもので示す。通過した検証は件数と結果だけ書き、実行したコマンドは並べない (読み手は再実行しない)。確認済み・推測・未検証を区別する。
- 失敗したチェック、省略した検証、残った問題は明記する。指摘・理由・推奨対応を欠落させない。
- 色だけで状態を示さず、要対応・未検証などの文字を添える。

## [判断] — 決めてもらう必要があるときだけ

事実は先に自分で調べ、人には好み・優先度・トレードオフを聞く。聞くことが無ければ書かない。報告の締めに問いを足すために判断を作らない。他案に利点がなければ実質 1 択なので、既存の権限内で進める。問いは通常 1〜3 件。

シートを出さない短い相談では、会話に次の形で書く。シートを出すときは同じ中身をシートの「要判断」に書き、会話にも質問ツールにも出さない (ダイアログがシートを隠し、問いが 2 か所に出る)。

```text
[判断] <問い1つ>
推奨: <案の名前> — <理由と根拠>
他案: <案の名前> — <利点> / <代償>
```

**返事がないことは承認ではない。** 実装前の合意など必要な承認は返答を待つ。既に承認された作業や、その範囲内の可逆な作業に確認を足さない。承認待ちと独立した調査は進めてよい。設計の承認をコミット・push・公開の依頼と解釈しない。

## 報告シート

HTML は手で書かず、短い Markdown を `scripts/new-sheet.py` に渡す。生成器が雛形への流し込み・検査・保存先の決定まで行う。書式・字数の上限・図の選び方は `references/sheet-input.md` にあり、初回に読む。

書く順:

1. 読み手が最初の画面で分かるべき要点を 1 つ決め、タイトル `# <状態の語> | <結論 1 文>` にする。状態の語は読み手がすることで選ぶ: 対応不要 / 要判断 n 件 / 要対応 / 未完了。
2. 図を描く。冒頭にタイトルの結論そのもの (何が起きるか) の図を 1 枚置き、そのあとも文より図の方が速く伝わる所には図を足す。枚数の上限は無い。足す所は、`優先` の指摘ごと (食い違いの型)、案の違いが形に出る要判断 (前後の型を `## 案の違い` などの自由な節に置く)、数や大きさを比べる所 (量の型)、流れや構成を説明する自由な節。どの図も、描く前に「この図だけで何が分かるか」を 1 文で言う。言えない、または表の行と同じ語を箱に並べるだけになるなら描かない。コードの処理の流れに印を付けただけの図にしない。不具合や指摘は「画面に出ること」と「実際」を 2 段に並べる。
3. 決めてもらう事項は 1 問ずつ `## 要判断:` にする。このとき `次:` は書かない (タイトルの「要判断 n 件」で伝わる)。要判断が無く、読み手がすることがあるときだけ `次:` を書く。
4. 一覧・指摘は `## 項目` に 1 行 1 項目で書く。経緯やログは `## 付録` に畳む。調査やレビューで説明・表・コードが要るなら `## <見出し>` の自由な節に普通の Markdown で書く。表やコードを省いて短くしない。
5. 生成する。Bash なら 1 回の呼び出しで済む。PowerShell では here-string をパイプで渡す:
   ```bash
   python "<skill dir>/scripts/new-sheet.py" - --name <英数字の題> <<'EOF'
   # 要判断 1 件 | ...
   EOF
   ```
   `NG` が出たら直して作り直す。`??` は読んで、必要なものだけ直す。
6. 生成器が出したシートの場所 (Orca では `::orca-visual` の行) を会話に貼る。詳細や `--save` のときは残した場所も書く。

## シートの見せ方 (環境別)

| 環境 | 保存と表示 |
|---|---|
| `ORCA_CHAT_SCRATCH_DIR` がある | new-sheet.py が scratch に置き、会話に貼る `::orca-visual{...}` の行を出す。残すもの (詳細と `--save`) は保存先に書き、scratch に写しを置く。別ブラウザは開かない |
| 通常のローカル環境 | シートは一時ディレクトリの `report-sheets/`、残すものは `output-config.toml` の保存先 (`--out` で決め打ちできる)。比較シートは `./review/<topic>.html`。会話に絶対パスのリンクを返す |
| 表示できない環境 | 保存だけして、絶対パスのリンクかファイル受け渡し手段で渡す。表示未検証と明記する |

環境の表示規約・ユーザー指定を優先する。Codex の会話には `[タイトル](/absolute/path/report.html)` 形式でリンクする。
