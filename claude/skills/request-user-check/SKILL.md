# request-user-check — 報告と相談の型

ユーザーへの報告と相談をすべてこの型で出す。読み手が最初の数行で状況をつかみ、決めることだけを決めて先へ進めるようにするため。
**Input**: 報告する結果、または決めてほしい論点。渡されていなければ、このセッションの直前の作業を報告する。報告できる作業も無ければ、何を報告・相談するかを 1 行で聞いて止まる。
**Output**: 会話での報告・相談。長くなる報告は HTML の報告シート、見た目で比べる論点があれば `./review/<topic>.html` の比較シートを加える。

Claude Code でも Codex でも同じ手順で動く。ツール名は環境に合わせて読み替える (質問ツールが無ければ会話で聞く、`Agent` ツールが無ければ試問を省く)。

## まずこれだけ (核)

1. 返信を書く前に数える。会話が **6 行を超える**、**3 項目以上の一覧・比較**、**問題やテスト結果が複数** のどれかなら、会話に書かず **報告シート** (表中心の HTML) にする
2. シートを出したら、会話は **結論 1 文 / シートの場所 / 注意点 / [判断]** だけ。シートの中身を箇条書きで繰り返さない
3. 図は任意。表で足りるなら描かない。形 (流れ・構造・前後・大小) が要るときだけ描く
4. 決めてほしいことは **[判断]** にし、**推奨を先頭** に書く。3±1 件まで
5. 手順は「報告シートの手順」。見た目で比べる論点だけ「比較シートの手順」。残りは下を読む

## 形を選ぶ

上から順に当てはめ、最初に当たった形を使う。

| 順 | 状況 | 形 |
|---|---|---|
| ① | 見た目で比べる論点がある (UI の配置・レイアウト・画面遷移の A/B) | **シート**: HTML の比較シートを開き、[判断] は会話で聞く |
| ② | 長文の原稿 (記事・README・レポート) を渡す | **原稿**: 原稿ファイルそのものを渡して開き、指摘は会話で受ける。要約に組み直さない |
| ③ | 報告・相談が会話で 6 行を超える、3 項目以上の一覧・比較になる、または見つけた問題・テスト結果が複数ある (行数は問わない) | **報告シート**: 中身を HTML 1 枚にまとめて見せ、会話には結論 1 文と [判断] だけ書く |
| ④ | 書いたコードの承認を取る (コミット前・方針が分かれる変更の後) | **差分**: 変更の要点、最初に見てほしい行 (`file:line`)、触っていない範囲を示し、判断の要る行に [判断] を付ける |
| ⑤ | 決めてほしいことがあり、文章だけで選べる | **相談**: 報告 + [判断]。質問ツールがあればそれで聞く |
| ⑥ | 報告だけ (決めてほしいことが無い) | **報告**: 会話で結論から書く |

ユーザーは長い文章を会話で読むのが負担なので、会話に書く分量を上の ③ の基準 (6 行) までに抑え、超える分は報告シートに移す。人が一度に覚えておける項目は 4 つ程度なので、会話で同時に持たせる事柄 (要点・注意点・[判断]) も 4 つまでにする。比較シートを作るのは、絵が無いと人が想像で補ってしまう論点があるときだけにする。

## 書く前に要点を 1 つ決める

報告を書く前に「読み手が 1 つだけ持ち帰るなら何か」を 1 文で決める。たいていは、読み手の次の行動を変える事実 (壊れていた・直った・選ぶ必要がある・危ない) がそれに当たる。

- 要点は 1 つ、多くても 2 つにする。全部を同じ強さで並べると、どれが大事か読み手に伝わらない
- 要点は報告の 1 文目かシートのタイトルに置く。シートでは図の中で要点だけを赤にし、残りは灰色にする
- 要点以外の、読み手が判断・行動・確認に使う情報 (各項目の中身・理由・直し方・注意点) は、短く書いて本文に出す。要点を 1 つに絞るのは強調のためで、他の項目を隠すためではない
- `<details>` に畳むのは、経緯・調べた手順・実行ログ・生データだけにする。畳みを閉じたまま読んでも、何が起きて、読み手が次に何をすればよいかが分かる形にする

## 報告の書き方

1. **1 文目は結果と要点** — 頼まれたことができたか、何が分かったか。経緯や手順から書き始めない
2. **根拠** — `file:line` や実行結果を引く。要点を支える分だけ書く
3. **[判断]** (相談のときだけ) — 下の書式で 3±1 件まで
4. **注意点** — 失敗したテスト、飛ばした作業、想定と違った挙動。あれば必ず書き、無ければ書かない

- 文字を減らす。1 文で言えることを 2 文にしない。言い換え、前置き、締めの要約を書かない
- 3 項目以上の一覧は、文章で書かず報告シートの表にする。流れ・構造・前後の違い・量の大小を説明したくなったときだけ、図も置く
- 箇条書きと見出しは、読みやすくなるときだけ使う。短い報告は普通の文章で書く
- 作業の中で作った呼び名を説明なしに使わない
- 「調べれば分かること」を人に聞かない。自分で調べて報告に書く

## 図の選び方

図は任意。描く前に「表で足りるか」を自問し、足りるなら図を置かない。形 (順序・分岐・入れ子・前後・大小) が分からないと伝わらないときだけ描く。調査結果や評価の一覧は表にする。「処理の流れ」の図に、表と同じ項目を並べ直しただけのものは置かない。

描くときは、伝えたい中身の形に合わせて選ぶ。文章で説明していた内容を、図のラベル (1 項目 15 字程度) に置き換える。

| 中身 | 図 | 要点の示し方 |
|---|---|---|
| 処理や作業の流れ | 箱を矢印でつなぐ | 問題の箱か矢印を赤くする |
| 構成・依存関係 | 箱の入れ子、線でつないだ箱 | 変えた箱を赤枠にする |
| 変更の前と後 | 左に前、右に後を並べる | 違う部分を赤くする |
| 複数項目の状態 (一覧・調査結果) | 項目 × 観点の格子に短い語 (「動かない」「未確認」)。✓ ✗ ! の記号は凡例を覚えさせるので使わない | 危ない行を赤くする |
| 量・内訳・時間 | 横棒 | 目立たせる棒を赤、他は灰色にする |

図は手書きのインライン SVG で描く。次の規則を守る。

- ノードは 12 個まで。矢印の交差が 2 つ以上になるなら図を分ける
- 入れ子は 2 階層まで
- 文字を消しても、形だけで意味が通る図にする。通らないなら表にする
- 描いたら画像にして目視確認し、ずれや文字の欠けを直してから出す。画像化できない環境では、シートを開いて確認する

## [判断] の書式

1 件 = 1 つの判断。人がその文面だけで即答できる形にする。

```
[判断] <問い 1 行>
推奨: <案の名前> — <理由> 根拠: <file:line か実行結果>
他案: <案の名前> — <利点> / <代償>
```

- **推奨を先に書く**。選択肢を全部読ませてから最後に推奨を出すと、読み手は各案を覚えたまま読み進めることになる
- **案は中身で呼ぶ** (「3 件だけ直す」「4 件とも直す」)。A・B のような記号で呼ぶと、読み手は記号と中身の対応を覚えておく必要がある。他案が 2 つあれば `他案:` の行を 2 行にする
- **他案にも利点を書く** (`/` の左)。利点が書けないなら実質 1 択なので、[判断] にせず推奨で進めて報告に書く
- 判断に要る数値は文面の中に書く。シートや別の箇所へ探しに行かせない
- シートがあるときは、問いの頭に論点の番号と名前 (「①ボタンの位置」) を付けて、どの絵の話かを示す
- 質問ツール (Claude Code の `AskUserQuestion` 等) があればそれで聞く。推奨の案を先頭に置き、ラベルに「(推奨)」と付ける。1 回の質問は 4 件まで
- 質問ツールが無ければ、会話に [判断] をそのまま書き、「返事が無い判断は推奨で進めます」と 1 回だけ添える

## 最重要禁則

- **承認の前に先へ進まない** — 実装前の相談なら、返事が来るまで実装しない。コミット前の確認なら、コミットも次の変更もしない
- **承認されてもコミットは依頼があるまでしない** — 承認はコミットの依頼ではない
- **事実を人に聞かない** — 各 [判断] に `file:line` か実行結果を添える。人に残すのは決定 (好み・優先度・トレードオフの裁定) だけ
- **[判断] は 3±1 件まで。5 件以上出さない** — 人の判断コストが本体。すべてに推奨を付け、返事が無くても進められる形にする
- **報告シートを作ったら、シートの中身を会話に書かない** — 会話は結論 1 文、シートの場所、注意点、[判断] だけにする。表や箇条書きを会話にも書くと、読み手は同じ内容を 2 か所で読むことになる
- **結果を盛らない** — 失敗・未確認・回避したことは、そのまま書く

## 報告シートの手順 (会話で書くと長くなるとき)

1. **書く** — `assets/sheet-template.html` ではなく `assets/report-template.html` を埋める。タイトルに要点を 1 行で書く。「図の選び方」の自問で図が要ると決めたときだけ、その下に図 (インライン SVG) を置き、要点にあたる図の要素だけを `class="key"` で赤くする。項目ごとの中身 (何が・なぜ・どう直すか) と根拠 (`file:line` か実行結果) を表で並べる。セルは句で書き、段落は置かない。経緯やログだけを `<details>` に畳む。[判断] はシートに書かない
2. **検査** — `python3 "<skill dir>/assets/check-sheet.py" <シートのパス>` を実行し、NG と ?? が出たら直す。TODO の残り、相対 URL、図がある場合の要点の印 (`class="key"`) の欠落、文字の多すぎ (本文 600 字・結論 80 字・表のセル 60 字の超過)、畳みが本文より長いことを検出する (`<skill dir>` は下の比較シートの手順の冒頭を参照)
3. **置いて見せる** — 下の「シートの見せ方」に従う
4. **会話に書く** — 次の型で書き、これ以外を足さない。シートに載せた項目を会話で箇条書きにし直さない

   ```
   <結論 1 文>
   <シートの表示 (またはパス)>
   <注意点 (シートを開く前に知るべきことがあれば 1 文)>
   <[判断] (あれば)>
   ```

## シートの見せ方 (環境別)

報告シートも比較シートも、保存したらこの節で見せる。

| 環境 | 手順 |
|---|---|
| 環境変数 `ORCA_CHAT_SCRATCH_DIR` がある (Orca のチャット) | そのフォルダに毎回新しい名前 (`<topic>-<4 桁の英数字>.html`) で保存し、会話に `::orca-visual{file="<ファイル名>" title="<タイトル>"}` を単独の行で書く。これだけで見せ終わり。頼まれていないのにブラウザでも開かない (ユーザーが「開いて」と言ったときだけ開く) |
| ブラウザを開ける (上以外) | 比較シートは `./review/<topic>.html`、報告シートは一時ディレクトリに保存して開く (Windows は `Start-Process <path>`、macOS は `open`、Linux は `xdg-open`)。パスも会話に書く |
| 開けない (リモートのコンテナ等) | パスを伝える。ファイルを渡す手段があればそれで渡す |

## 比較シートの手順 (見た目で比べる論点があるとき)

`<skill dir>` は、この SKILL.md が置かれているディレクトリを指す。`~/.claude/skills/request-user-check/` など、skill として置いた場所。分からなければ、この SKILL.md 自身のパスから求める。

## Gotchas

- **報告シートは表を中心にする** — 一覧・調査結果・不具合は、項目ごとの中身・どうするか・根拠を並べた表で見せる。図を足すかは「図の選び方」の自問で決める。図で足せるのは形だけで、表の中身を図に写し直さない
- **検査スクリプトが `python3` で動かないとき** — Windows では `python3` が Store の空スタブで失敗することがある。`py -3` か `python` で同じスクリプトを実行する

- **シートに問いを並べない** — 問いは会話の [判断] に置き、シートには絵・対比表・根拠だけを載せる。両方に書くと、人は同じ問いを 2 か所で読むことになる。論点の場所は ①②③ の印だけで示す
- **現物と乖離したモックを描かない** — 既存画面に手を加えるなら、現行 UI の忠実な再現が信頼の根になる
- **シートは self-contained にする** — 相対 URL を使わない。画像は data URI か https の絶対 URL。モックへのリンクは `file://` の絶対 URL (Windows はスラッシュ 3 本: `file:///C:/path/to/mock.html`。空白は `%20`)
- **試問の subagent を background で立てない** — 結果が返る前に応答を終えると、検査をしないまま人に出すことになる
