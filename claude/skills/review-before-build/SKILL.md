# review-before-build — 実装前レビュー

作る前に 1 案を人に見せ、人の回答・訂正を受け取ってから作るためのワークフロー。
**Input**: 見せたい 1 案 (UI 配置・設計・方針、または長文の原稿) + 決めてほしい論点。
**Output**: 人がブラウザで開く HTML (`./review/<topic>-01.html`) と、人がそこで [貼り付ける文章を作る] を押してターミナルに貼り戻す【レビュー回答】テキスト。
サーバ不要・外部ネットワーク不要。HTML 1 枚が `file://` で完結し、回答はターミナルに貼るだけ。

## まずここで止まる — このスキルを使わない条件

レビューは確認コストを人に払わせる道具で、シート 1 枚の作成は小規模な実装より重いことがある。
**下のどれかに当てはまるなら、シートを作らずに済ませる。** 該当したら、その場でその手段に切り替える。

| 状況 | 代わりに使う手段 |
|---|---|
| **対象が既に書いたコード・差分・PR** — 「レビューして」がコードレビューの意味 | `self-review` / `code-review` / `my-code-review`。**このスキルは書く前の案にだけ使う** |
| 決めてほしいことが 2 問以下、または返答が候補 1 つで完結する (方針・命名・優先度など見た目の差が無いもの) | `AskUserQuestion` で直接聞く |
| 答えが事実で一意に決まる (コードを読めば分かる、実行すれば分かる) | 自分で調べて決める。人に聞かない |
| 多数アイテムの一括検収 (100 件の分類結果を承認 等) | 別の道具。レビューの対象外 |
| 人が既に方針を明示していて、確認は儀式にしかならない | そのまま実装する |

**使うのは、絵にしないと判断できない論点があるときだけ。** UI の配置・画面遷移・レイアウトの A/B のように、文章で説明すると人が想像で補ってしまい、結果として全問「お任せ」に倒れる論点。ここがレビューの本領で、それ以外では純粋な損失になる。

## 最重要禁則

- **【レビュー回答】が届く (貼られる) 前に実装を始めない** — 確認ゲートの意味が消える。待つ間は別作業をする
- **レビューは視覚物への訂正であって、質問票ではない** — UI や画面が対象なら、現物の再現 (スクショ埋め込みか DOM 再現) を必ず載せる。質問だけのシートが許されるのは、方針や優先度など絵にできない論点だけ
- **選択肢の対立軸は両方絵にする** — A と B の違いが絵で見えない問いは出さない。推奨案の挿絵だけ並べて選択肢を文字 1 行にすると、人は想像で補えず全問お任せに倒れる。**回答フォームの選択肢にも同じ絵を付ける** (`.thumb`) — 人はシートを読んでからフォームで答える。フォームで絵が消えると想像で補わせることになる。見た目の無い選択肢 (方針・優先度) には付けない
- **事実を人に聞かない** — 各問に `file:line` か実行結果の引用を添える。人に残すのは決定 (好み・優先度・トレードオフの裁定) だけ
- **「決めてほしいこと」は 3±1 問、5 問以上並べない** — 人の判断コストが本体。各問に未選択 = お任せ + (推奨) を明記し、未回答でも進められる形にする
- **現物と乖離したモックを描かない** — 既存画面に加えるなら、現行 UI の忠実な再現が信頼の根
- **正解が一意で自己検証できることは聞かない** — レビューは好みや曖昧な仕様が左右する判断だけに使う
- **長文の読み物を要約したシートに組み直さない** — 訂正対象の本文が人の目から消える。指摘モードか添削モードで原稿そのものを見せる

## モード選択

| モード | 対象 | 人がすること | 使う asset |
|---|---|---|---|
| **標準** (迷ったらこれ) | UI 配置・設計・方針の 1 案 | 問いカードに答える + 全体へのコメント | `assets/sheet-template.html` |
| **指摘** (shiteki) | 記事・README・長文レポート。直すのは agent | 原稿そのままの体裁で、段落タップか文字なぞり → チップ (削る / 短くする 等 7 種) + ひとこと | `assets/shiteki/kit-template.html` + `assets/shiteki/README.md` |
| **添削** (tensaku) | 人が本文を直接書き換えて完成形を返したい長文 | HTML 内で段落を直接編集 (直す / 完成形 / 差分のタブ) | `assets/tensaku/build-sheet.py` + `assets/tensaku/README.md` |

返答の型で決める。人が「指摘・注文を返す」なら指摘、「本文を書き換える」なら添削、それ以外は標準。3 モードとも [貼り付ける文章を作る] ボタンが `references/reply-format.md` の固定形に整形するので、agent の読み方は 1 つで済む。ボタン文言はテンプレと案内文で揃えてあるので変えない。

## assets のパス

以下の手順で `<skill dir>` と書いた箇所は、**この SKILL.md が置かれているディレクトリ**を指す。導入方法で変わる。

- skill ディレクトリを配置した場合: `~/.claude/skills/review-before-build/` (この dotfiles では `claude/install.ps1` がここへ展開する)
- plugin として入れた場合: `${CLAUDE_PLUGIN_ROOT}/skills/review-before-build/`

分からなければ、この SKILL.md 自身のパスから求める。

## 手順

1. **不使用条件の確認** — 冒頭の表に当てはまらないことを確かめる。当てはまるならシートを作らずにその手段へ切り替える
2. **現物把握** — 既存 UI ならスクショかコードから忠実に再現する。ゼロからの構想なら図解でよい。長文モードは原稿を用意する
3. **モード選択** — 上の表で決める
4. **シートを書く**
   - 標準: `assets/sheet-template.html` を `references/sheet-spec.md` の規約で埋める。骨格は動かさない。動く論点 (操作感・頻度) があれば、モックを `./review/mock/` に置き、シートの冒頭に `file://` リンクのボタンを置く
   - 指摘: `assets/shiteki/README.md` の手順で移植する (原稿 HTML に kit の 2 ブロックを移す / kit の `<article>` に原稿を流し込む、のどちらか)。問いの差し替え方も同 README
   - 添削: `python3 "<skill dir>/assets/tensaku/build-sheet.py" <記事.md> <label> "<タイトル>" -o ./review/<topic>-01.html`。`-o` が出力先。他の引数は `--help` を参照
5. **問いを 3±1 問に圧縮** — 各問は自己完結カード。問い 1 行 + 各選択肢の利点/代償 1 行ずつ + 判断に要る数値の再掲 + 未選択 = お任せ (推奨)。非推奨の選択肢にも「選ぶ理由」を 1 行書く。カードだけ読めば答えられる形にする。添削モードは 0 問
6. **埋め忘れ検査 (標準モードのみ)** — `python3 "<skill dir>/assets/check-sheet.py" ./review/<topic>-01.html` を実行する。`CHANGE-ME` の残り、radio name と `QUESTIONS` のズレ、`.thumb` の欠落など、無言で壊れる不備を機械的に検出する。添削モードは `build-sheet.py` が生成時に落とすので不要。**指摘モードは生成器を通さない手作業の移植なので、`assets/shiteki/README.md` の「移植後の確認」を目視で通す**
7. **試問 (preflight)** — `references/preflight.md` の 5 問を、`Agent` ツールで立てた文脈ゼロの subagent に出す。渡すのはシートのパスと読者宣言 1 行だけ。**`model=sonnet` を指定する** (読者役に上位モデルは要らない)。**同期で結果を待つ (background にしない)。結果を受け取るまで応答を終えない。** 落ちた問いは絵を加える / 落とす / 言い換える。計 2 巡で打ち切る。添削モードは問いが 0 なので試問を省く。短い原稿 (1 画面程度) なら 1 巡で打ち切ってよい
8. **保存して開く** — `./review/<topic>-01.html` に保存する。macOS は `open`、Linux は `xdg-open`、Windows は `cmd /c start ""` で `file://` のまま表示する。開けない環境 (ssh・コンテナ) では絶対パスと `file://` URL を提示して人に開いてもらう
9. **待つ** — 「ブラウザで回答して、[貼り付ける文章を作る] で出たテキストをここに貼ってください」と伝えて応答を終える
10. **反映** — 貼られた【レビュー回答】を `references/reply-format.md` の規則で読み、反映する。添削モードは書き戻しの作法 (差分行ではなく「完成形 Markdown 全文」を記事ファイルへ戻す) が `assets/tensaku/README.md` にあるので、反映前に Read。お任せの問は (推奨) 案で確定。設計が変わる指摘なら `<topic>-02.html` で再往復し、捨てた案は取り消し線で残す
11. **証跡** — HTML は消さずに残す (git 管理下ならシートの commit を推奨)。「なぜこの設計か」の答えになる。**反映後の原稿・コードの commit は人に確認してから** (シートの commit とは別扱い)

## Gotchas

- **クリップボード自動コピーは環境により失敗する** — textarea 表示が正。textarea をクリック (全選択) して手動コピーで足りる
- **`open` が無い環境** (ssh・コンテナ) では手順 8 を「絶対パス + `file://` URL の提示」に切り替える
- **Windows の `file://` URL はスラッシュ 3 本** — `file:///C:/path/to/sheet.html`。`file://C:\path\...` はクリックで開けない。パスに空白があれば `%20` に置換する
- **試問の Agent を background で立てない** — 結果が返る前に応答を終えると、人にシートを見せる前の検査が抜けたまま進む
- **DRAFT_KEY はシートごとに一意に** — 回答の下書きは localStorage に保存される。使い回すと別のシートの下書きが復元される
- **`crypto.randomUUID` をテンプレの script に加えない** — file:// や社内 http 配信で undefined になり全滅する。id は固定文字列でよい
- **質問の radio name (q1, q2, …) と script 内 QUESTIONS を同期する** — ズレた質問は回答プロンプトに載らず、無言で「お任せ」扱いになる。手順 6 の `check-sheet.py` が検出する
- **長文モードの原稿は往復中に凍結する** — 指摘のアンカーは DOM 順のブロック番号、添削の差分の土台は生成時の記事。差し替えると人の指摘がずれる。直すなら `-02.html` として作り直す
- **問いをシートの先頭に置かない** (標準モード) — 問いを記憶したまま説明を読ませる形になる。指摘モードの冒頭の設問ブロックは例外 (原稿全文が同じ画面にある)
