# root-cause-debug

原因を確かめる前に直さない。推測で直すと、症状が消えても原因が残るか、別の場所に移る。

## 1. 観察する

直す前に、次を自分で確かめる。

- エラーメッセージとスタックトレースを最後まで読み、ファイル・行・エラーコードを控える
- 再現手順を決め、実際に再現させる。再現しないなら、推測で直さず情報を集める
- 直近の変更を見る（`git diff`、`git log -5`、依存や設定の変更、環境の違い）
- 処理が複数の部品をまたぐとき（CI → ビルド → 署名、hook → スクリプト → 外部コマンドなど）は、境界ごとに入力と出力を 1 回だけ記録して、どの境界で値が壊れるかを先に特定する
- 壊れた値は、呼び出し元をさかのぼって作られた場所を突き止め、そこで直す

## 2. 比べる

- 同じリポジトリの中で、似ていて正しく動くコードを探す
- 動くものと動かないものの違いを、小さなものまで全部書き出す。「これは関係ないはず」で外さない
- 参考実装やドキュメントに沿って書いたコードなら、参考側を飛ばし読みせず読む

## 3. 仮説を 1 つずつ確かめる

- 仮説は「X が原因だと考える。根拠は Y」の形で 1 つだけ立てる
- 仮説を確かめる最小の変更か観察を 1 つだけ行う。複数を同時に変えない
- 外れたら変更を戻し、新しい仮説を立てる。外れた修正の上に別の修正を重ねない
- 分からないときは分からないと書き、ユーザーに聞くか調べる

## 4. 直す

- できれば先に、不具合を再現して失敗するテストか使い捨てのスクリプトを作る
- 原因の箇所だけを 1 回で直す。ついでのリファクタリングや周辺の書き換えは入れない
- 再現手順と既存のテストを流し、症状が消えたことと他が壊れていないことを確かめる（`verify-before-done`）

## 修正が 3 回外れたら止まる

同じ不具合で修正が 3 回外れたら、4 回目を試さずに止まる。直すたびに別の場所で症状が出る、共有状態や結合が次々に見つかる、直すには大きな書き換えが要る、という状態なら、設計の前提が合っていない可能性が高い。それまでに分かったことと、設計を見直す案をユーザーに示して判断を仰ぐ。

## 報告

原因の報告には、確かめた事実（再現した、ログで見た）と推測を分けて書き、根拠を file:line で示す。原因が特定できないまま症状だけ止めた場合は、そう書く。
